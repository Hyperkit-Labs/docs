## Interview objective

The interview program exists to answer one question. Do high-fit teams already lose enough time or money across specification, generation, audit, simulation, and deployment to adopt an integrated workflow product.

The interviews should therefore be treated as evidence collection, not as product marketing. Each conversation should clarify current behavior, current spend, recent workflow failure, and the threshold for behavior change.

## Recruitment design

### Warm intros

Use warm intros from:

1. founder networks
2. hackathon contacts
3. ecosystem partners
4. trusted technical peers

Purpose:
Fast access to high-context interviews and deeper workflow detail.

### Cold outreach

Use cold outreach through:

1. GitHub
2. open-source communities
3. chain-specific builder groups
4. security and audit communities

Purpose:
Reduce founder-network bias and test whether the problem generalizes beyond friendly audiences.

## Variables to measure

### Background variables

1. role
2. team size
3. number of chains used
4. shipping cadence
5. contract type

### Pain variables

1. workflow stages used
2. most painful stage
3. stage where confidence drops most
4. delay frequency
5. stage where failure is most costly

### Spend variables

1. last audit cost
2. simulation tooling cost
3. deployment-service cost
4. contractor or advisor cost
5. internal engineering time cost

### Behavior variables

1. current toolchain
2. repeated manual workarounds
3. custom scripts or checklists
4. release coordination process
5. last failed or delayed workflow

### Adoption variables

1. willingness to test on a live workflow
2. return intent
3. buying motion
4. budget owner
5. pricing sensitivity

## Core interview sequence

1. Map the last real smart contract project.
2. Reconstruct the exact workflow from idea to deployment.
3. Identify the painful stage and the risky stage.
4. Quantify what was spent to reduce that pain.
5. Test whether one integrated workflow would change current behavior.

## Strong questions

1. Tell me about the last smart contract project shipped by the team.
2. What were the exact stages from idea to deploy.
3. Which stage consumed the most time.
4. Which stage felt the most risky before going live.
5. What tools were used for audit, simulation, and deployment.
6. What did the team already pay to reduce that pain.
7. What was the last workflow mistake that cost time, money, or momentum.
8. Which one stage would be removed first if the workflow could be simplified.

## Anti-patterns

1. Do not ask whether the product sounds cool.
2. Do not ask future-price questions first.
3. Do not start with feature requests.
4. Do not treat compliments as validation.

## Success threshold

The interview program succeeds only if high-fit users describe:

1. repeated workflow pain
2. meaningful time or money spent on workarounds
3. clear willingness to test on a real workflow

The interview program fails if responses remain generic, flattering, or future-facing. The relevant signal is present pain tied to concrete behavior.

## Reflection

1. Are the interviews measuring pain, spend, and behavior separately.
2. Is the team oversampling friendly contacts.
3. Are workflow questions grounded in the last real project rather than in hypotheticals.
4. Do the answers produce evidence strong enough to confirm or falsify the hypothesis.
